# Unity 방 조명 수동 작업 가이드

기준일: **2026-10-22** · Unity **6000.2.8f1** · URP **17.2.0**

**작업 목표: 현재 Ingame 씬과 방 프리팹 생성 구조를 유지하면서, 실시간 Light 없이 연결된 방의 조명을 미리 굽습니다.**

이 문서는 조명 작업자가 Unity에서 직접 배치·조정할 때 사용하는 안내입니다. 이번 문서 작성으로 씬·프리팹·CSV·URP 설정·게임 코드를 변경하거나 베이크하지 않았습니다. 아래 수치는 품질 시험용 제안이며 측정으로 확정한 최적값이 아닙니다.

## 1. 씬과 방 연결에 대한 기준

### 1.1 새 런타임 씬은 필요하지 않습니다

Ingame 안에서 방 프리팹을 생성하고, 이미 열린 방을 유지하는 현재 방식을 사용합니다. 방별 Additive 씬 분리는 이 가이드의 전제가 아닙니다. Lighting Settings나 Lighting Data 같은 **에셋 파일이 생성되는 것과 새 게임 씬을 만드는 것은 다릅니다.**

```text
Ingame — 하나의 게임 공간
  1번 방 ← 문을 통해 서로 보임 → 2번 방 ← → 3번 방 … 7번 방
     └──────── 이미 생성한 방은 유지하고 자유롭게 왕복 ────────┘

에디터: 최종 연결 배치 재현 → 조명 조정 → 베이크 → 데이터 저장
실행 중: 기존 CSV로 방 생성 → 저장한 조명 연결 → 이전 방과 함께 표시
```

### 1.2 방 단위 연출과 베이크 단위는 구분합니다

각 방의 전등 색·밝기·분위기는 별도로 설계할 수 있습니다. 하지만 문을 통해 이웃 방이 보이므로 **실제로 이어지는 위치에 방들을 놓고 함께 검토·베이크**하는 것이 기본입니다. 최종 품질 검사는 해당 역할의 1~7번 방이 모두 연결된 상태를 기준으로 합니다.

1번 방과 2번 방을 각각 원점에서 따로 구워 붙이면 문턱의 밝기·반사·간접광이 어색할 수 있습니다. 모든 방을 함께 굽더라도 라이트맵 텍스처가 방마다 한 장씩 자동 생성되는 것은 아닙니다. Unity의 아틀라스 배치는 별도이며 한 장을 여러 방이 공유할 수 있습니다.

A/B는 별도 클라이언트이므로 **A의 최종 배치와 B의 최종 배치를 따로 검토**합니다. 같은 위치에 A/B 내부 물체를 겹쳐 놓고 한 번에 굽지 않습니다. 고정 가구가 서로 다르면 그림자와 빛 반사도 달라지므로, 외벽이 같다는 이유만으로 베이크 결과까지 공용화하지 않습니다.

## 2. 현재 구현과 추가 연결이 필요한 부분

현재 Unity 프로젝트 위치: `C:/Users/m/Desktop/listen`

| 확인 대상 | 현재 코드·파일 기준 상태 | 작업 시 의미 |
|---|---|---|
| `Assets/1.Scene/Ingame.unity` | Directional Light와 Skybox 환경 설정이 있으며 전용 Lighting Settings 참조는 없음 | 아직 완성된 방별 베이크 환경으로 판단하지 않음 |
| `Assets/3.Script/World/IngameWorldDriver.cs` | CSV의 RoomPrefabID로 프리팹 생성, 로드한 방 유지 | 씬을 나누지 않고 현재 로더 유지 가능 |
| `Assets/3.Script/World/RoomSceneView.cs` | CSV 앵커에 역할별 내부 프리팹 생성·기능 구성 | 조명 작업 배치도 동일한 앵커·역할 선택을 재현해야 함 |
| 게임 스크립트의 라이트맵 처리 | `LightmapSettings`·`lightmapIndex`·`lightmapScaleOffset` 복원 코드 검색 결과 없음 | 구운 결과를 실행 중 프리팹에 연결하는 기능은 후속 작업 |
| `Assets/3.Script/Editor/RoomClearPreviewSession.cs` | Ingame Play 모드에서만 실행, `DontSave` 임시 복제본 사용 | **배치·이동 확인용이며 베이크 저장용이 아님** |
| `Assets/3.Script/World/RoomConnectionAlignment.cs` | 입구·출구에 맞춰 방 루트 위치·회전 정렬 | 베이크도 정렬 후 최종 위치가 기준 |
| 방 정렬 호출 | 확인한 직접 호출은 에디터 미리보기·검사 코드에 있음 | 테스트에서 연결됐다는 이유만으로 실제 입장 배치까지 같다고 가정하지 않음 |
| `Assets/3.Script/Interaction/CloseupPreview.cs` | UI 모델을 먼 좌표에 복제하고 `PreviewLight` Directional Light를 실행 중 생성 | 게임 전체 실시간 Light 제거 시 이 경로도 별도 변경 필요 |

**지금 가능한 일:** 전등 배치·색·범위·고정 물체 GI 분류·프로브 배치와 조명 시안 제작입니다.

**아직 자동으로 되지 않는 일:** Room Clear Test 결과 저장, CSV 배치의 편집 모드 자동 재현, 역할별 베이크 저장·선택, 런타임 프리팹 라이트맵·프로브 복원입니다. Unity의 일반적인 Generate Lighting만 수행해도 이 기능이 추가되는 것은 아닙니다.

현재는 Play를 종료한 뒤 Ingame에서 수동으로 최종 배치를 재현해 작업할 수 있습니다. 제작 배치를 게임 씬에 남기는 경우 런타임 자동 생성과 중복되지 않도록 후속 연결 검토가 필요합니다. 베이크된 방이 실제 플레이에 연결되기 전까지 편집 화면의 조명 확인과 실제 게임 적용 완료를 구분합니다.

## 3. 조명별 역할과 오브젝트 분류

### 3.1 기본 정책

| 요소 | 이 프로젝트의 사용 기준 | 의도 |
|---|---|---|
| Baked Point/Spot/지원되는 Area Light | 고정 실내 조명 | 방의 빛과 그림자를 사전 계산 |
| 라이트맵 | 고정된 큰 표면 | 벽·바닥·천장의 밝기 차이와 고정 그림자 표현 |
| 기존 Light Probe Group | 동적 물체가 다니는 공간 | 저장된 주변 조명을 문·손·무전기 등에 반영 |
| Baked Reflection Probe | 금속·광택 표현이 필요한 방 | 저장된 반사 영상 사용 |
| Realtime/Mixed Light | 사용하지 않음 | 실시간 Light 계산 제외 |
| 실시간 반사 캡처 | 사용하지 않음 | 실행 중 큐브맵 재촬영 제외 |

Directional/Point/Spot은 조명 모양이고 Baked/Mixed/Realtime은 계산 방식입니다. Point로 바꾸기만 해서는 베이크가 되지 않습니다. Baked Light의 직접광·간접광은 라이트맵과 프로브에 미리 저장됩니다. [Unity Light Modes](https://docs.unity3d.com/6000.2/Documentation/Manual/LightModes-introduction.html)

### 3.2 고정 배경과 동적 물체

| 오브젝트 | Contribute GI | Receive Global Illumination / Light Probes | 주의 |
|---|---|---|---|
| 벽·바닥·천장·문틀 | 켬 | Lightmaps | 실제 렌더링 MeshRenderer에서 설정 |
| 절대 움직이지 않는 큰 가구 | 필요 시 켬 | Lightmaps | 완성된 위치로 고정 |
| 작은 소품 | 필요성에 따라 선택 | 프로브 우선 검토 | 작은 물체마다 라이트맵을 크게 배정하지 않음 |
| 열리는 문짝·돌아가는 다이얼 | 끔 | Light Probes: Blend Probes | 움직이는 물체의 고정 그림자를 굽지 않음 |
| 손·무전기·플레이어 임시 모델 | 끔 | Light Probes: Blend Probes | 이동 높이까지 프로브가 있어야 함 |

움직이는 물체는 부모·자식 어느 쪽에서도 정적 베이크 대상으로 묶이지 않았는지 확인합니다. 문짝을 제외해도 문틀은 따로 굽습니다. 무조건 부모의 Static 전체 체크를 켜서 움직이는 자식까지 적용하지 않습니다.

## 4. 수동 작업 순서

### 4.1 배치를 먼저 고정합니다

1. Play 모드를 종료합니다. Play 중 만든 임시 복제본은 제작 원본으로 사용하지 않습니다.
2. Ingame에서 **한 역할의** 방·고정 내부 소품을 CSV 기준으로 배치합니다. 자동 편집 모드 구성 도구는 아직 없으므로 현재는 수동 재현입니다.
3. 처음에는 1번 방과 2번 방을 함께 배치해 시안을 만듭니다. 최종 베이크 전에는 해당 역할 전체 연결 공간을 확인합니다.
4. `R01_DoorPoint`와 `R02_EntryPoint`처럼 실제 연결점 기준으로 방을 맞춥니다. 다음 출구는 `R02_DoorPoint`입니다. 연결점 이름·축 규칙은 기존 정렬 코드와 동일하게 유지합니다.
5. 문턱·바닥 높이·겹친 벽·빛이 새는 틈을 확인합니다. 런타임 배치가 이 위치·회전·스케일을 재현해야 합니다.
6. 사용할 역할과 CSV 버전을 기록합니다. 서버 CSV로 플레이할 때도 같은 배치가 되는지 이후 검사합니다.

조명만 맞추려고 CSV 앵커 이름·ID·방 연결점을 임의로 바꾸지 않습니다. 배치가 바뀌면 기존 베이크와의 정합성을 다시 확인합니다.

### 4.2 모델과 머티리얼을 준비합니다

1. 고정 배경의 MeshRenderer에서 Contribute GI와 Receive GI=Lightmaps를 확인합니다.
2. FBX에 적절한 라이트맵 UV가 없다면 Project에서 FBX 선택 → Model Inspector → **Generate Lightmap UVs**를 검토하고 Apply합니다. 이미 작업된 UV가 있다면 품질을 비교한 뒤 결정합니다.
3. 벽과 바닥의 UV 겹침·얇은 면·뒤집힌 노멀·중복 면을 확인합니다. 빛샘을 무조건 해상도로 해결하지 않습니다.
4. 조명을 받아야 하는 표면은 URP Lit 등 베이크 조명을 지원하는 머티리얼인지 확인합니다. Unlit은 같은 방식으로 조명을 받지 않습니다.

라이트맵 UV 생성은 모델 임포트 설정과 결과 데이터에 영향을 주므로 변경 파일을 기록합니다. 원본 FBX를 단순히 압축하는 옵션과는 역할이 다릅니다. [Unity 라이트맵 UV 생성](https://docs.unity3d.com/6000.2/Documentation/Manual/LightingGiUvs-GeneratingLightmappingUVs.html)

### 4.3 기존 Directional Light와 환경광을 정리합니다

1. 기존 Directional Light가 실내 분위기를 덮지 않도록 조명 시안 단계에서 비활성화하고 비교합니다. 테스트용이라면 바로 삭제하기보다 의도를 기록합니다.
2. Window → Rendering → Lighting에서 **Environment** 설정을 확인합니다.
3. 창문 없는 실내라면 Skybox에서 들어오는 밝은 환경광·반사가 의도에 맞는지 확인합니다. 낮은 환경광부터 실내 전등을 조정합니다. 환경광을 무조건 0으로 고정하지는 않습니다.
4. 씬 조명의 영향을 보는 Scene 뷰에서는 기본 편집용 조명 대신 씬 조명을 사용하도록 확인하고, 최종 판단은 Game 뷰에서 합니다.

Directional Light만 꺼도 주변광과 반사는 남을 수 있습니다. 반대로 실내 베이크가 준비되지 않은 상태에서 끄면 어두워지는 것이 정상입니다.

### 4.4 방 안에 Baked Light를 배치합니다

1. GameObject → Light에서 Point 또는 Spot Light를 만듭니다. 넓은 발광 면은 URP/베이커가 지원하는 Baked Area Light도 후보입니다.
2. **Mode=Baked**를 확인합니다. Mixed나 Realtime을 사용하지 않습니다.
3. 아래 조절표 순서로 색·범위·밝기를 맞춥니다. 물체 내부에 광원을 넣으면 가려질 수 있으므로 발광 면과 실제 광원 위치를 확인합니다.
4. 가능하면 방 프리팹 아래 조명 전용 부모를 두어 관리합니다. `R01_Lighting` 같은 이름은 **작업용 제안**이며 기존 CSV 앵커로 등록된 이름은 아닙니다.

| 사용자가 조절할 항목 | 조절 목적 | 작업 기준 |
|---|---|---|
| 위치·회전 | 어느 표면을 강조할지 결정 | 먼저 실제 전등 위치와 맞춤 |
| Color / Color Temperature | 방의 따뜻함·차가움 | UI 단서의 색을 구분할 수 있어야 함 |
| Range | 영향을 줄 거리 | 문 너머까지 의도치 않게 밝아지지 않는지 확인 |
| Intensity | 조도 조절 | 노출·머티리얼 조건이 달라 절대값을 일괄 지정하지 않음 |
| Spot Angle | 비추는 폭 | 퍼즐 강조와 벽면 연출에 사용 |
| Emission | 전등 표면이 밝아 보이는 정도 | 표면 발광과 주변을 비추는 결과를 구분 |

### 4.5 Lighting Settings를 만들고 시험 베이크합니다

Lighting 창에서 **New Lighting Settings** 또는 해당 설정 에셋 생성 기능을 사용해 Ingame에 연결합니다. **새 씬 생성은 하지 않습니다.** Unity 화면 언어에 따라 표시 이름은 달라질 수 있습니다.

| 설정 | 처음 시험할 기준 | 설명 |
|---|---|---|
| Baked Global Illumination | 켬 | 베이크 사용 |
| Realtime Global Illumination | 지원 UI가 보이면 끔 | URP에서 보이지 않는 항목은 억지로 찾지 않음 |
| Auto Generate | 자동 베이크 옵션이 있으면 끔 | 수동 조절 후 명시적으로 생성 |
| Lightmapper | 사용 가능한 Progressive CPU/GPU | 제작 PC의 베이크 시간·메모리에 영향. 게임의 실시간 Light와 별개 |
| Lightmap Resolution | 예: 10~20 texels/unit에서 비교 | 1 unit≈1m라는 전제의 초깃값. 실제 방 스케일과 화면 결과로 조정 |
| Max Lightmap Size | 우선 1024에서 확인 | 아틀라스 한 장의 최대 크기이며 전체 메모리 한도가 아님 |
| Lightmap Compression | 우선 Normal Quality | 어두운 벽의 압축 얼룩도 확인 |
| Directional Mode | Non-directional과 Directional 비교 | 메모리 우선이면 전자, 노멀맵 방향감이 중요하면 후자 검토 |

벽 노멀맵이 중요한 현재 아트에서는 Non-directional로 바꿨을 때 표면이 평평하게 보이는지 반드시 비교합니다. Directional은 추가 방향 텍스처를 사용합니다. 샘플 수는 먼저 기본값으로 확인하고 노이즈가 남을 때 높입니다. **샘플 수와 해상도는 역할이 다릅니다:** 전자는 주로 베이크 시간·노이즈, 후자는 텍스처 밀도·메모리에 영향을 줍니다. [Unity Lightmapping 설정](https://docs.unity3d.com/6000.2/Documentation/Manual/Lightmaps-reference.html)

Generate Lighting을 실행하고 완료 후 씬·설정·생성 조명 데이터를 저장합니다. 처음에는 1~2번 방 시안으로 비교하고, 확정 시 전체 연결 배치를 다시 베이크합니다. 프리팹 Apply만으로 라이트맵 연결까지 저장됐다고 판단하지 않습니다.

## 5. 방 연결부와 움직이는 문

### 5.1 문을 열어도 이전 방은 그대로 보입니다

라이트맵은 해당 방의 Renderer가 가진 조명 정보입니다. 두 방의 오브젝트가 같은 Ingame 공간에 유지되고 조명 연결이 올바르면, 열린 문 너머 이전 방도 함께 렌더링할 수 있습니다. 이를 위해 방을 다른 씬으로 옮길 필요는 없습니다.

검토할 위치는 문턱 양쪽, 문틀, 바닥 접합부, 복도 모서리입니다. 카메라를 문 바로 앞·문턱 위·다음 방 안에 두고 이전 방을 바라보며 비교합니다. 프로브의 밝기 변화도 같은 위치에서 확인합니다.

### 5.2 문짝의 그림자를 고정 배경에 굽지 않습니다

문짝은 Contribute GI를 끄고, 베이크에 실제로 가림·그림자를 남기지 않는 상태인지 결과를 확인합니다. 문틀과 벽은 고정 배경으로 베이크합니다. 문짝 자체는 프로브로 밝기를 받습니다.

실시간 조명을 사용하지 않으므로 문이 회전하는 동안 문 그림자가 바닥을 따라 움직이거나, 열린 순간 다음 방 빛이 새롭게 퍼지는 효과는 발생하지 않습니다. 정적 조명은 기본적으로 열린 연결 공간의 최종 분위기를 기준으로 연출하고, 닫힌 문은 화면을 가리는 역할을 합니다. 닫힌 방의 물리적으로 정확한 암부와 문을 열었을 때의 빛 변화를 동시에 요구하면 조명 상태 전환 같은 별도 구현이 필요합니다.

### 5.3 배치 확정 이후의 변경

방 루트를 런타임에 이동·회전시키는 경우 벽 라이트맵만 복원하는 것으로 충분하지 않습니다. 프로브 위치·방향, 반사 프로브, 이웃 방과의 간접광 관계도 함께 검토해야 합니다. 이 프로젝트의 첫 적용은 **정렬된 최종 배치를 고정하고 그 배치를 그대로 재현**하는 기준이 안전합니다.

## 6. 라이트 프로브와 반사 프로브

### 6.1 기존 Light Probe Group 사용

1. 편집 모드의 최종 연결 공간에 GameObject → Light → Light Probe Group을 배치합니다.
2. Edit Light Probes로 플레이어 이동 공간을 감싸도록 점을 배치합니다.
3. 바닥 한 높이에만 두지 않고 낮은 높이·손/눈 높이·상부 높이가 있는 입체 볼륨을 만듭니다.
4. 방 중앙은 간격을 넓히고, 전등 주변·어두운 구석·문 양쪽처럼 밝기가 크게 변하는 곳에 보강합니다.
5. 점을 벽·천장·가구 안에 넣지 않습니다. 벽 너머 다른 방의 밝기가 섞여 보이면 배치를 조절합니다.
6. 문짝·손·무전기 Renderer의 Light Probes를 Blend Probes로 확인합니다. 여러 손 부품이 서로 다른 밝기로 보이면 공통 Probe Anchor 사용을 검토합니다.
7. 조명과 함께 베이크하고, 이동 중 밝기 튐과 문턱에서의 색 변화를 확인합니다.

점 수를 많이 늘리는 것보다 빛 변화가 있는 위치를 잡는 것이 우선입니다. **Light Probe Group 프리팹에 점 위치를 저장하는 것만으로 구운 조명 계수까지 런타임에 등록되지는 않습니다.** 현재 로더에는 이 연결도 후속 작업입니다. 기존 프로브 방식과 APV를 동시에 전제로 삼지 않으며, 이번 가이드는 기존 Light Probe Group을 기준으로 합니다. [Unity 프로브 배치](https://docs.unity3d.com/6000.2/Documentation/Manual/class-LightProbeGroup.html)

### 6.2 금속 자물쇠·다이얼을 위한 Baked Reflection Probe

1. 반사가 필요한 방에 Reflection Probe를 추가하고 Type=Baked를 선택합니다.
2. 영향 영역을 해당 방의 범위로 맞춥니다. 문 경계에서 두 프로브의 영향이 어색하게 바뀌는지 확인합니다.
3. 우선 해상도 128 정도의 낮은 값에서 비교하고 꼭 필요한 경우만 높입니다. 반사가 중요하지 않은 방은 생략합니다.
4. Box Projection이 필요하면 Probe와 사용 중인 URP Asset 양쪽 지원 설정을 확인합니다.
5. 베이크된 큐브맵을 저장하고, 실행 중 매 프레임 갱신하거나 Realtime Type을 사용하지 않습니다.

반사 프로브는 방을 밝히는 전등이 아닙니다. 금속이 검게 보인다고 조명 Intensity부터 크게 높이지 말고 반사 환경도 확인합니다. [Unity Reflection Probe 설정](https://docs.unity3d.com/6000.2/Documentation/Manual/class-ReflectionProbe.html)

### 6.3 Closeup 미리보기는 별도 확인이 필요합니다

현재 Closeup은 모델을 `(10000,10000,10000)` 부근에 복제하고 전용 카메라·실시간 Directional Light로 표시합니다. 방 프로브를 배치해도 이 복제본이 방 조명을 그대로 받는 구조는 아닙니다.

게임 전체에서 실시간 Light를 없애려면 후속으로 미리보기의 표현 전략도 바꿔야 합니다. 후보는 조작 상태를 반영하는 Unlit 전용 UI 머티리얼, 또는 별도 저장 조명 데이터를 사용하는 미리보기입니다. **지금 PreviewLight만 삭제하면 자물쇠가 어둡게 보일 수 있으므로 수동 삭제만으로 완료 처리하지 않습니다.** 이번 문서에는 현황과 작업 경계만 기록하며 코드는 수정하지 않았습니다.

## 7. 품질과 리소스 조절

| 증상·목표 | 먼저 조절할 것 | 피할 조절 |
|---|---|---|
| 빌드 용량·GPU 메모리 감소 | 불필요한 베이크 대상, Scale In Lightmap, 해상도, 방향 텍스처, 반사 해상도 | 모든 방 아틀라스를 무조건 크게 생성 |
| 벽 그림자가 거칠음 | 해당 표면의 texel 밀도·UV·필요한 부분의 Scale In Lightmap | 작은 소품까지 전체 해상도 일괄 증가 |
| 간접광 노이즈 | 샘플·필터·광원 배치 | 샘플 증가가 곧 런타임 메모리 절감이라고 판단 |
| 어두운 면에 얼룩 | UV·압축·노이즈를 각각 비교 | 모든 텍스처의 압축을 일괄 해제 |
| 손 밝기가 튐 | 프로브 배치·보간 영역·Probe Anchor | 전역 환경광을 크게 올려 방 분위기 상실 |
| 금속이 검게 보임 | 반사 프로브·머티리얼·주변 밝기 | 실시간 Light 추가로 대체 |

현재 게임은 이전 방을 유지하므로 마지막 방까지 연 뒤의 라이트맵·반사 메모리가 중요합니다. 방을 화면에서 숨긴다고 이미 로드한 텍스처 메모리가 자동 해제되지는 않습니다. 방별 파일 수보다 전체 아틀라스 해상도·장수·포맷·참조 수명을 측정합니다.

GPU 렌더링 비용 감소와 빌드 용량 감소는 같은 지표가 아닙니다. 베이크는 저장 데이터를 추가해 실시간 조명 계산을 줄이는 방식입니다. 라이트맵 읽기와 프로브 보간 등 렌더링 비용 자체가 0이 되는 것은 아닙니다.

## 8. Play·빌드 검사와 문제 해결

### 8.1 조명 제작 검사

- [ ] Play 모드가 아닌 최종 제작 배치에서 베이크했다.
- [ ] A/B 고정 물체가 겹쳐 굽히지 않았다.
- [ ] 모든 실내 Light가 Baked이며 Mixed/Realtime이 없다.
- [ ] 기존 Directional Light·Skybox 환경광의 영향이 의도에 맞는다.
- [ ] 문짝·손·다이얼의 고정 그림자가 배경에 남지 않는다.
- [ ] 문턱에서 다음 방과 이전 방을 볼 때 밝기·반사가 자연스럽다.
- [ ] 금속·퍼즐 문자·카드 색을 읽을 수 있다.

### 8.2 런타임 연결 개발 이후의 검사

- [ ] Join → 실제 입장 경로로 생성한 방이 편집 화면과 같은 조명이다.
- [ ] Room Clear Test에서도 생성된 방의 라이트맵·프로브가 연결된다.
- [ ] 다음 방 생성 후 기존 방의 라이트맵 인덱스가 바뀌거나 덮어써지지 않는다.
- [ ] 문을 통과하며 손·무전기의 밝기 변화가 자연스럽다.
- [ ] 1~7번 방을 누적 생성하고 이전 방으로 왕복해도 유지된다.
- [ ] A와 B의 데이터·베이크 버전을 각각 확인했다.
- [ ] Closeup을 열어도 실시간 PreviewLight가 생성되지 않는 후속 표현으로 전환됐다.
- [ ] 기존 `client/build/Stable` 출력 정책에 따라 실제 빌드를 비교했다.

현재는 런타임 조명 연결이 없으므로 위 항목을 이미 통과한 것으로 보고하지 않습니다. 특히 Room Clear Test는 조명 데이터 제작 도구가 아닙니다.

### 8.3 원인별 확인

| 문제 | 확인 순서 |
|---|---|
| 씬에서는 괜찮고 실행 중 생성한 방만 어두움 | 라이트맵 등록·Renderer 매핑·프로브 데이터 연결 확인 |
| 다음 방 로드 후 이전 방 조명이 잘못됨 | 전역 lightmaps 배열 덮어쓰기·인덱스 충돌·다른 역할 데이터 선택 확인 |
| 문을 열어도 그림자가 남음 | 문짝이 베이크에 가림 물체로 포함됐는지 확인 후 재베이크 |
| Directional Light를 껐는데 전체가 밝음 | 환경광·Skybox·Emission·기존 베이크·반사 확인 |
| 문턱 양쪽 바닥 밝기가 다름 | 최종 연결 위치와 함께 굽혔는지, 각 광원 범위·재질·UV 밀도 확인 |
| 편집 모드 베이크에 방이 없음 | 방이 Play 모드에서만 생성되는 현재 구조인지 확인 |
| Closeup만 어둡거나 밝음 | 원본 방이 아니라 전용 복제 모델·카메라·Light 경로임을 확인 |

## 9. 후속 개발 연결 설계

**이 절은 제안이며 구현된 기능이 아닙니다.** 조명 작업자가 수동으로 lightmapIndex 같은 내부 숫자를 입력하는 방식으로 만들지 않습니다.

```text
기존 CSV: ROOM_A / ROOM_B → RoomPrefabID → PREFAB
             ↓ 최종 역할·앵커·연결 위치 재현 (편집 모드 도구 필요)
사용자 수동 조명 조절 → 베이크
             ↓ 저장·검증 (도구 필요)
역할·배치 버전별 조명 데이터
  ├─ Lightmap 텍스처 + Renderer별 인덱스·UV 영역
  ├─ 프로브 위치 + 구운 조명 계수
  └─ 반사 큐브맵 + 영향 영역
             ↓ 등록·복원 (런타임 Adapter 필요)
기존 방 생성 → 최종 위치 확정 → 조명 연결 완료 → 방 준비 완료
```

| 책임 | 연결 기준 |
|---|---|
| 데이터 선택 | 역할·ROOM.ID・최종 배치 버전 기준으로 매칭. 방 번호만으로 A/B를 혼동하지 않음 |
| 에디터 도구 | CSV 배치 재현·사용자 조명 보존·베이크 결과 수집·참조 검증 |
| 조명 데이터 | 불변 에셋으로 텍스처·매핑·프로브 저장. 현재 CSV에는 조명 프로필 컬럼이 없음 |
| 런타임 조명 Adapter | 전역 lightmaps 배열 등록·인덱스 보정·Renderer 복원·프로브 적용 |
| 방 로더 | 최종 배치와 조명 연결이 끝난 시점을 준비 완료로 정의 |
| 이벤트 | RoomLoaded를 완료 통지로 쓴다면 조명까지 연결한 뒤 발행하도록 순서 검토 |
| 수명 | 새 방이 이전 데이터 등록을 덮어쓰지 않음. 같은 조명 묶음 중복 등록 방지, 게임 종료 시 소유 자원 정리 |
| 서버 | 기존 정답·문 허가·해금만 담당. 조명 텍스처나 Unity Renderer를 통신 계약에 넣지 않음 |

이 경계는 기존 데이터 기반 선택·생성자/조립 의존성 주입·완료 이벤트 구조를 유지하기 위한 것입니다. 방마다 조명 처리 코드를 복사하거나 모든 로컬 동작을 이벤트 버스로 감싸지 않습니다. 저장된 베이크 텍스처를 추가하는 일과 네트워크 API를 추가하는 일은 별개입니다.

Renderer에는 lightmapIndex와 lightmapScaleOffset을 함께 연결하고, 그 인덱스가 전역 LightmapSettings.lightmaps의 올바른 항목을 가리켜야 합니다. 프로브는 Renderer 매핑만으로 해결되지 않으므로 데이터 등록·보간 구조도 검토합니다. [라이트맵 인덱스](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/Renderer-lightmapIndex.html), [UV 영역](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/Renderer-lightmapScaleOffset.html), [전역 라이트맵 목록](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/LightmapSettings-lightmaps.html)

## 10. 작업 기록과 공유 파일

### 10.1 재베이크가 필요한 변경

고정 방 배치·스케일·가구·광원 위치/밝기/색·고정 머티리얼의 반사/발광·UV·GI 분류·프로브 배치가 바뀌면 영향을 검토하고 재베이크합니다. 문 연결 위치가 바뀌면 이웃 방 경계도 다시 확인합니다. 베이크 데이터 생성 전후의 CSV 역할·프리팹 변경을 기록합니다.

### 10.2 같이 공유할 것

수정한 씬·프리팹·Lighting Settings·Lighting Data·라이트맵 텍스처·반사 큐브맵·모델 임포트 `.meta`와 기타 변경 에셋의 `.meta`를 함께 검토합니다. 후속 베이크 프로필 도구가 생기면 프로필 에셋도 포함합니다. 생성 폴더를 통째로 임의 삭제하거나 `.meta`를 새로 만들지 않습니다. `Library`와 로컬 GI 캐시를 공유하는 것으로 대체하지 않습니다.
